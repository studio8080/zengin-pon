# 既存FBのローカル読取・診断・逆変換（次段階の設計）

今回のアプリには読取機能をまだ接続しない。差分MVPの入力は表のみ。以下は次段階の受入プロファイル案であり、全銀行の形式対応を示すものではない。

## 最初に限定する形式: ZP120-v1

- 現在の `src/zengin.js` が生成する総合振込21・給与11・賞与12、コード区分0、各レコード120 **バイト**。
- 文字はJIS X 0201の既存 `encode/decode` が可逆に扱える1バイト範囲。UTF-8・UTF-16・2バイトShift_JIS・BOMは拒否。見た目の文字数で120を判定しない。
- 1ファイル1件のヘッダー1 → データ2（1行以上）→ トレーラ8 → エンド9。複数依頼・連結ファイルは対象外。
- 改行なし、LF、CRLFを個別に受け付け、混在・CRのみ・途中の空行は拒否。改行ありは全レコード同じ方式とし末尾も同じ改行を必須とする。
- ヘッダー: 種別2桁、依頼人コード10、依頼人名40、日付MMDD4、銀行4/15、支店3/15、種目1、口座7、予備17。レコード種別を含め120。
- データ: 種別1、銀行4/15、支店3/15、交換所4、預金種目1、口座7、名義30、金額10、新規コード1、識別領域20、後続9。
- 総合21の識別領域は顧客コード1/2各10、後続は振込区分7/8・EDI識別空白・予備7。EDI識別Yの自由文字領域、XML、銀行独自拡張は対象外として明示拒否。
- 給与11/賞与12の識別領域は社員番号10・所属コード10、後続は予備9。
- トレーラは件数6・合計12・予備101、エンドは予備119。予備の空白、新規コード0/1/2、数値フィールド・名義許容文字・件数・金額の整合性を検査。
- MMDDから年を推測しない。年は利用者が指定する。2/29は年指定後に検査する。顧客コードの0埋めだけでは人物IDの存在と見なさない。

## 安全な段階

1. ファイル名・サイズ・バイト配列をローカルメモリで受け、利用者に上記プロファイルを選ばせる。未知形式は「未対応」と停止し、近似形式へ自動補正しない。サイズ10MB・行数上限を設ける。
2. 不変の元バイトと検査結果を分離。行・バイト位置・規則・期待値・実値をローカルに表示する。エラーを直して受け入れたことにしない。重複口座や識別子は警告で明示し、集計から勝手に除かない。
3. 全検査成功後に表へ逆変換し、種別・元の識別領域・改行・元バイト長と金額合計を見せる。CSVの式として解釈されるセルはエスケープする。原本を書き換えない。
4. 別操作で前月・今回の比較へ渡す。安定識別子の指定と曖昧さの規則は差分MVPを再利用する。
5. 元バイトへのラウンドトリップと、独立に記述したオフセットfixtureで検証する。読取時に「送金済み」や「銀行受入保証」とは表示しない。

## fixture と依存条件

`node test/make-reader-fixtures.js` で `test/fixtures/fb-reader/` に人工データと `manifest.json` を生成する。正常候補は21/11/12 × 改行3種の9件。異常は長さ119、未知種別、未知コード区分、トレーラ不整合、混在改行、UTF-8、EDI拡張、複数ヘッダー、末尾改行欠落。manifestの期待は**将来パーサの受入契約**であり、現時点でパーサが合格したという証拠ではない。`test/reader-fixtures.test.js` はfixture自体の長さとオフセット・件数・合計を独立確認する。

実装前に、銀行の現行仕様書と利用許諾を一次情報で照合し、匿名化ではなく人工fixtureを追加する。実際に利用する銀行固有の形式がこのプロファイルと異なる場合は別プロファイルを設計し、推測で拡張しない。ブラウザごとの文字コード・境界・メモリ使用量と逆変換CSVの式注入対策を検証してから公開する。送金・銀行API・クラウドOCRは対象外。
