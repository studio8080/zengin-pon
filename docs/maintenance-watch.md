# 定期点検の項目（毎週）

作成: 2026-10-06。クラウドの定期エージェント（Claude Code のルーティン「全銀ポン 週次点検」、毎週月曜 10:00 JST）が
このファイルを読んで点検する。**項目を増やす・減らすときは、このファイルを直す**（ルーティンの設定は触らなくてよい）。

金融機関の辞書データの取り込みは、エージェントではなく GitHub Actions（`.github/workflows/update-dict.yml`、毎週）が行う。
エージェントの役目は「辞書データに出る前の動き」と「法令・仕様・技術の変化」を拾い、ページや設定との食い違いを見つけること。

---

## 進め方の決まり

1. まず `AGENTS.md` を読む。そこに書いてある禁止事項（振込データを外に出さない、AI を製品に使わない、事実でないことを書かない など）が最優先。
2. **一次情報で確かめたことだけを扱う。** 法令は e-Gov 法令検索・官報・所管省庁（金融庁・消費者庁・個人情報保護委員会・総務省・国税庁）、
   金融機関は各行のニュースリリース・金融庁の免許一覧・全銀協、仕様は全銀協・全銀ネット・ゆうちょ銀行の公式ページ。
   報道やまとめ記事だけで判断しない（きっかけには使ってよい）。条文番号は原文で確かめる。
3. **既に報告した事項を繰り返さない。** ラベル `定期点検` の Issue（閉じたものも含む）を先に読み、新しい事実だけを扱う。
4. 何も変化が無い週は、Issue も PR も作らない。
5. 施行日・発効日が先の事項は「いつ・何を直すか」を書いて報告する（先回りしてページを書き換えない）。

## やってよいこと／いけないこと

| してよい | してはいけない |
|---|---|
| 事実の確かな軽い修正を PR にする（古くなった日付・リンク切れ・改称した銀行名の表記・廃止された仕様への言及・CI のバージョン上げ） | `main` に直接 push する（push すると本番に出る） |
| PR の中で `node tools/build-site.js` を回す（`<!-- site:xxx -->` の中は手で直さない） | 料金・制限・契約条件・法令の解釈を変える（Issue で報告して運営者が決める） |
| 利用者に関わる修正なら `updates.html` に日付つきで追記する | `firebase deploy`、Stripe の設定・キー、秘密鍵、GitHub の設定に触る |
| 判断が要る事項を Issue にまとめる | 辞書データ（`data/`）を手で書き換える（取り込みは Actions の PR で行う） |
| | ページに AI 向けの指示文・隠しテキスト・実在しない評価を書く |

PR を出す前に `AGENTS.md` の「5. テストと確認」のテストを全部（`license.test.js` は秘密鍵が要るので除く）と
`node tools/build-site.js --check` を通す。

## 点検項目

### A. 金融機関（辞書に出る前の動き）

- 合併・統合・改称・営業譲渡の**予定**（発表済みで未実施のもの）。各行のニュースリリース、金融庁の報道発表で確かめる。
  - 実施日、旧→新の金融機関コード・支店コードの扱い（据え置き／変更）を調べる。
  - 実施日の前後で利用者が困ること（旧コードのまま作ったファイルが取り込めない など）があれば、
    `index.html` のお知らせ帯・該当する銀行ページへの案内を Issue で提案する。
- 支店の統廃合・店舗内店舗化・支店名やコードの変更の予定（大きなもの。例: 数十店の一括統合）。
- 新しく開業・廃業する金融機関（ネット銀行、信金・信組の合併）。
- 辞書の元データ `zengin-code/source-data` の最終更新日と、`data/version.json` の版を比べる。
  元データが2か月以上更新されていない、または実施済みの合併が反映されていなければ報告する。
- `update-bank-dictionary`（Actions）の直近の実行が失敗していれば、ログから原因を調べて報告する（新しい辞書でテストが落ちた場合は、どの銀行・支店の変化が原因かまで）。
- 開いている `auto/update-dict` の PR があれば、差分（増えた・消えた・改称）を要約して、その PR にコメントする。

### B. 全銀フォーマット・振込の仕組み

- 全銀協・全銀ネットの仕様変更（総合振込の固定長 120 バイト、文字コード、XML 電文・ZEDI、全銀システムの更改）。
- 名義に使える文字の基準（長音・中点・小さいカナ・記号の扱い）の変更。
- ゆうちょ銀行の記号番号 → 店名・口座番号の変換ルール、振込受付の変更。
- 主要行のインターネットバンキング（法人向け）の総合振込ファイルの取込仕様の変更・サービス終了の告知。
- 照合先: `zengin-format.html`、`guide.html`、`src/` の変換ロジック、`tools/verify_zengin.py`。

### C. 法令・制度

`docs/compliance-check.md` の「関係する法令」の表にある法令について、改正・ガイドライン改定・パブリックコメント・施行日の到来を調べる。

- 銀行法（電子決済等代行業の範囲）、資金決済法
- 特定商取引法（通信販売の表示、12条の6 の最終確認画面、ガイドライン）
- 個人情報保護法（いわゆる3年ごと見直し、外国にある第三者への提供、委員会規則・ガイドライン）
- 電気通信事業法（外部送信規律）
- 消費者契約法、景品表示法（比較広告・ステルスマーケティング）
- 障害者差別解消法、JIS X 8341-3 の改正
- インボイス制度（当社は未登録。経過措置の控除割合が変わる日など、購入者への説明に影響するもの）
- 照合先: `legal.html`、`tokushoho.html`、`privacy.html`、`terms.html`、`pricing.html#confirm`、`faq.html`、`accessibility.html`、`docs/compliance-check.md`。
- 法令の解釈が絡むものは PR にせず、Issue に「何が変わる／当社のどの記述に関係しそう／確認先」を書く。

### D. 検索・AI 検索

- Google 検索セントラルの更新（構造化データの廃止・変更、スパムポリシー、サイトマップ）、Bing・IndexNow の変更。
- AI クローラーの新しいユーザーエージェント（`robots.txt` は検索・引用系と学習用を分けて書いてある）。
- 照合先: `tools/build-site.js` の構造化データ、`robots.txt`、`llms.txt`。

### E. 技術・依存関係

- GitHub Actions のアクション・ランナーの非推奨（例: Node.js 20 で動くアクションの廃止）。`.github/workflows/` を照合。
- Cloud Functions の Node.js ランタイムの廃止予定（`functions/package.json` の `engines`）、`firebase-functions` `firebase-admin` `stripe` `nodemailer` の重大な脆弱性・メジャー更新。
  **関数のコードは PR にしてよいが、デプロイは運営者が行う**ので、PR 本文に「マージ後に `firebase deploy --only functions:zenginpon --project misefits` が必要」と書く。
- Stripe の API・Webhook の変更で、`functions/` が呼んでいる API に関係するもの。
- ブラウザの変更（ファイル読み込み・ダウンロード・文字コードまわり）で動かなくなるおそれのあるもの。

### F. 四半期に1回（1・4・7・10月の最初の点検だけ）

- 比較表の相手（銀行・信金の配布ツール、他の変換サービス）の料金・対応形式。調査日を更新する。
- `llms.txt`・`pricing.html`・`faq.html`・構造化データ（offers）の料金表記が、実際の料金と一致しているか。
- リンク切れ（外部リンク）。

## 報告の形

Issue のタイトル: `定期点検 YYYY-MM-DD`、ラベル: `定期点検`。本文は次の順で書く。

```
## 要対応（期限つき）
- [ ] 事項 — 何が変わる／いつ／当社のどこに関係するか／出典URL（確認日）
## 確認待ち（運営者の判断が要る）
## 参考（今は対応不要）
## 出した PR
## 確かめられなかったこと
```

GitHub の Issue・PR を作る手段が使えないときは、`claude/` で始まるブランチに `docs/watch/YYYY-MM-DD.md` として同じ内容を置いて push する。
