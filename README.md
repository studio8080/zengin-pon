# 全銀ポン — 事業計画・仕様メモ

作成: 2026-09-03。Excel / CSV / PDF の振込一覧を全銀協フォーマット（FBデータ）に変換し、
ネットバンキングにそのまま取り込めるようにするWebツール。ブラウザ内だけで処理する。

このリポジトリには **計画（このファイル）** と **動くMVP**（`index.html` + `src/`）が入っている。

```
zengin-fb/
  index.html          画面（4ステップのウィザード: ファイル → 列の確認 → 振込元 → 確認・DL）
  style.css
  config.js           公開設定（Google連携のクライアントID等。秘密情報は置かない）
  src/zengin.js       変換エンジン（依存なし・Node/ブラウザ両用）
  src/organize.js     表の自動整理（見出し推定・結合セル分解・値の形からの列推定・合計行除外）
  src/dict.js         金融機関辞書の読み込み＋名前→コードの逆引き
  src/gsheets.js      Googleスプレッドシート連携（Picker + drive.file + Drive export）
  src/app.js          画面ロジック（SheetJS / pdf.js は CDN）
  test/organize.test.js 自動整理のテスト（5件）
  data/banks.json     金融機関辞書（tools/build-dict.js で生成、元は zengin-code）
  data/branches/      銀行ごとの支店一覧（必要な分だけ取得）
  data/merged.json    統廃合の旧→新コード表（手で管理）
  tools/build-dict.js 辞書ビルド。DICT_VERSION=YYYY-MM-DD node tools/build-dict.js [source-data dir]
  .github/workflows/update-dict.yml  毎月の辞書自動更新PR
  test/zengin.test.js node test/zengin.test.js で実行（12件）
  samples/            総合振込・給与振込のサンプルCSV
```

ローカル起動: `python -m http.server 8765 --directory zengin-fb` → http://127.0.0.1:8765/

## 1. 結論（先に）

- **技術的リスクは低い。** 全銀フォーマットは固定長120バイト×4種のレコードで、仕様は公開されている。
  MVPはこのリポジトリで既に動いている（Excel/CSV→全銀、名義の半角カナ変換、法人略語、ゆうちょ変換、検証、ダウンロード）。
- **事業的リスクは「無料の代替が多い」こと。** freee・マネーフォワード・弥生給与はFBデータを標準出力する。
  ネット銀行（楽天・住信SBI・GMOあおぞら・PayPay等）はCSVを直接受け付ける。銀行自身が無料のExcel変換ツールを配っている例もある。
- したがって狙うのは **「給与・支払を今もExcelで回していて、メガバンク・地銀・信金のネットバンキング（全銀形式のみ）を使っている小規模事業者」** と、
  **「顧問先の振込データを何社分も作る社労士・税理士事務所」**。この層は今でも手入力か、古いフリーソフトを使っている。
- 差別化は (1) **ブラウザ完結でデータを預からない**（口座情報を外部に出さない安心感） (2) **名義カナの自動変換と事前チェック**（銀行側でエラーになる前に止める）
  (3) **PDF入力**（給与ソフトの「振込一覧表PDF」しか手元にないケース） (4) **列割り当ての記憶**で2回目以降は本当に一発。

**総合振込.jp が無料で存在する意味**（2026-09-03 確認）

- 「Excel→全銀変換」そのものは、もう無料が相場。変換機能だけに課金するのは難しい。
- 同サイトは広告（会計ソフトのアフィリエイト）で回している。同じモデルで後発が勝つのは難しい。
- 差別化して課金できる余地は次の4つ。
  1. **金融機関辞書との照合と統廃合の警告**（同サイトには無い。銀行で弾かれる前に気づける）
  2. **複数の振込元プロファイル**（社労士・税理士事務所が顧問先ごとに切り替える）
  3. **PDF入力**（給与ソフトの「振込一覧表PDF」しか手元に無いケース）
  4. **サポートと継続性**（辞書の毎月更新、銀行別の取込条件の整備、問い合わせ対応）
- 現実的な価格帯は「無料枠あり＋事務所向け有料（月額 1,000〜3,000円）」。個人事業主から広く薄く取るのは無理筋。

**ターゲット**

1. 従業員5〜50人、給与計算はExcel／社労士任せ、振込はメガバンク・地銀・信金の法人ネットバンキング
2. 社労士・税理士事務所（顧問先ごとに依頼人情報を切り替えて何本も作る → 「複数プロファイル」機能が刺さる）

## 3. 全銀フォーマット仕様（実装済み）

全レコード120バイト固定長。文字コードは JIS X 0201（Shift_JIS の1バイト部分）。
使える文字: 数字・英大文字・半角カナ・記号 `( ) - . / ¥ ｢ ｣` ・空白。
濁点は分離（ﾊﾞ = ﾊ + ﾞ）。行末は CR+LF が一般的（銀行により「区切りなし」指定あり）。

### ヘッダーレコード（データ区分 1）

| 項目 | 桁 | 型 | 内容 |
|---|---|---|---|
| データ区分 | 1 | N | 1 |
| 種別コード | 2 | N | 21=総合振込 11=給与振込 12=賞与振込 |
| コード区分 | 1 | N | 0=JIS |
| 振込依頼人コード | 10 | N | 銀行から付与される委託者コード |
| 振込依頼人名 | 40 | C | 半角カナ |
| 振込日 | 4 | N | MMDD |
| 仕向銀行番号 | 4 | N | |
| 仕向銀行名 | 15 | C | 空白可 |
| 仕向支店番号 | 3 | N | |
| 仕向支店名 | 15 | C | 空白可 |
| 預金種目 | 1 | N | 1=普通 2=当座 |
| 口座番号 | 7 | N | |
| ダミー | 17 | C | 空白 |

### トレーラ（8）・エンド（9）

- トレーラ: `8` + 合計件数(6) + 合計金額(12) + 空白(101)
- エンド: `9` + 空白(119)

### 名義カナ変換ルール（`Zengin.toZenginChars`）

- 全角カナ・ひらがな → 半角カナ、濁点分離、全角英数 → 半角、英小文字 → 大文字
- 拗音・促音 ｬｭｮｯ → 大文字（銀行慣行。オプションでオフ）
- 法人略語: 株式会社→ｶ、有限会社→ﾕ、合同会社→ﾄﾞ、医療法人→ｲ、一般社団法人→ｼﾔ、NPO→ﾄｸﾋ など約40種。
  先頭は `ｶ)`、末尾は `(ｶ`、中間は `(ｶ)`。営業所→`(ｴｲ`、出張所→`(ｼﾕﾂ`
- 中点「・」→「.」、各種ハイフン → `-`、「￥」「\」→ `¥`
- 変換できない文字（漢字など）は残してエラー表示 → 画面で直接修正できる

### ゆうちょ銀行（記号・番号 → 店番・口座番号）

- 総合口座（記号 1xxx0）: 店番 = 記号2〜3桁目 + `8`、普通、口座番号 = 番号の末尾「1」を除く7桁
- 振替口座（記号 0xxxx）: 店番 = 記号2〜3桁目 + `9`、当座、口座番号 = 番号を7桁0埋め
- 銀行コード 9900

## 3b. 銀行コード・支店コードの扱い（統廃合・名称変更への対応）

### 原則: コードが正、名前は飾り

全銀フォーマットで銀行が見るのは **銀行コード（4桁）と支店コード（3桁）** だけ。銀行名・支店名の欄は
任意で、ほとんどの銀行がコードから自動で補う。だから統廃合で名前が変わっても、コードが正しければ通る。
問題になるのは **コード自体が変わる／廃止される** ケースで、これは「辞書」で検知するしかない。

### 金融機関辞書（`data/`）

- 元データ: [zengin-code/source-data](https://github.com/zengin-code/source-data)（MIT）。全銀協の公開ページから
  収集されたもので、ほぼ毎月更新されている（直近 2026-08-24）。1,146 金融機関・28,944 支店。
- `tools/build-dict.js` で `data/banks.json`（全行）と `data/branches/XXXX.json`（支店、必要な銀行分だけ読む）に変換して同梱。
- **アプリ本体を触らずに辞書だけ差し替えられる。** `.github/workflows/update-dict.yml` が毎月2日に最新版を取得し、
  差分があれば PR を作る。マージすれば GitHub Pages に反映される。画面の下部に「金融機関一覧: YYYY-MM-DD 版」と出る。

### 画面での使い方

| 状況 | 画面の扱い | 出力 |
|---|---|---|
| コードが辞書にある | 銀行名・支店名を表示。空欄なら辞書のカナで補完（オプションで停止可） | 出力できる |
| 銀行コードが辞書にない | 「確認」（黄）: 統廃合か入力ミスの可能性 | 出力できる（銀行で弾かれる可能性を明示） |
| 支店コードがその銀行の一覧にない | 「確認」（黄） | 出力できる |
| `data/merged.json` に旧コードとして登録済み | 「確認」（黄）: 新コードと切替日、支店番号の扱いを表示 | 出力できる |
| 桁数不正・空欄・使えない文字 | 「エラー」（赤） | 出力できない |

警告を「出力不可」にしない理由: 辞書の更新が銀行の変更より遅れることがあるため。
最終判断は銀行側のチェックに委ね、こちらは「気づかせる」役に徹する。

### 統廃合が起きたときの運用

1. 月次の自動PRで辞書が更新される（新コードが載り、旧コードが消える）。
2. 旧コードが消えた金融機関を `data/merged.json` に「旧→新、切替日、支店番号の扱い（引き継ぎ／再採番）」として手で追記する。
   これで旧コードのままの Excel を持ち込んだ利用者に「新コード XXXX に直してください」と案内できる。
3. 支店の再採番がある合併（同じ支店コードが別支店になる）では自動変換はしない。利用者が銀行からの通知で直すのが正しい。
   ツールは「この銀行は YYYY-MM-DD に合併し支店番号が変わっています」と出すだけにする。
4. ゆうちょ銀行は記号・番号→店番・口座番号の変換規則が固定なので辞書に依存しない。

### 辞書の限界（正直に書く）

- zengin-code は個人メンテのOSS。止まった場合は全銀協の公開ページ（金融機関コード検索）から自前で収集する
  スクリプトを `tools/` に追加する。データ形式は同じにしてあるので差し替えは容易。
- 「支店の統廃合で支店コードが変わった」レベルの履歴は辞書に無い。旧支店コードは単に「一覧にない」警告になる。

## 3c. 「並びが揃っていない表」の自動整理（`src/organize.js`）

前提: 利用者のExcelは全銀の項目順になっていない。AIは使わず、全部ルールで整理する（2026-09-03 決定:
**AI API・クラウドOCR・AIによる誤入力判定は使わない**。データを外に出さない設計と、判定の再現性を優先）。

| 起きること | 対応 |
|---|---|
| 見出しが2行目以降、タイトル行が上にある | 見出し語の一致数と「数値が無い行」で見出し行を採点して選ぶ。手動で行を選び直せる |
| 見出しが無い | 値の形（4桁／3桁／5〜8桁／金額／カナ／漢字名／銀行文字列／支店文字列／普通・当座）で各列を判定して割り当てる。画面に「推定」バッジ |
| 見出しがあっても中身が違う（「銀行」列に銀行名） | 見出し一致でも値の形が矛盾する列は採らない |
| 1セルに複数項目（`0005-001`、`普通 1234567`、`三菱UFJ銀行 渋谷支店`、`山田太郎（ヤマダタロウ）`） | 6割以上の行で同じ分解ができる列は「元→項目」という仮想列に分けて右に追加する |
| 銀行コードが無く銀行名しかない | 金融機関辞書で名前→コードを逆引き（「信用金庫」等の語でコード帯を絞る。候補が複数なら「確認」で提示） |
| 支店コードが無く支店名しかない | 同じく支店一覧から逆引き |
| 合計・小計行 | 「合計」等の語、または名義も口座も無く金額だけの行を除外 |
| 口座番号と金額の区別（どちらも数字だけ） | 先頭0や7桁固定なら口座番号、下2桁00が多ければ金額。見出しがあればそちらが優先 |

限界: 縦持ち（1人1ブロック）の表や、1セルに3つ以上の自由記述が混ざるものは対象外。
推定は必ず画面で確認させる（「推定」バッジと「例」列）。同じ見出しのファイルは手直しを記憶する。

## 3d. Googleスプレッドシート連携（`src/gsheets.js`）

「ピッカーで選んで直接読む」方式。仕組みは3ステップ。

1. Google Identity Services でログインし、スコープ `drive.file`（利用者が選んだファイルだけ触れる権限）のトークンを得る
2. Google Picker（Googleが用意しているファイル選択ダイアログ）でスプレッドシートを選ばせる。Picker で選んだファイルは `drive.file` の対象になる
3. Drive API の `files.export` で xlsx として取得し、いまの SheetJS 経路に流す

通信は利用者のブラウザと Google の間だけ。自社サーバーは通らない。`drive.file` は非機密スコープなので Google の審査は不要。
必要な設定と手順は `config.js` の冒頭に書いた（GCPプロジェクト、Drive API / Picker API 有効化、OAuth同意画面、クライアントID、APIキー）。
未設定の間はボタンを押すと「ファイル→ダウンロード→Excel」の案内を出す。

## 3f. 課金の仕組み（2026-09-10 実装）

**サーバー不要の署名付きライセンスキー**にした。Misefits の Firestore 方式より軽く、「通信しない」という売りとも整合する。

```
発行側（手元のPC）                          利用者のブラウザ
tools/issue-key.js ── Ed25519 秘密鍵 ──▶ ZP1-<payload>.<署名>  ──▶ src/license.js が公開鍵で検証 → localStorage に保存
   ~/.zengin-pon/license-private.pem              payload = {v:1, p:"pro", e:"有効期限", id}
```

- 秘密鍵: `C:\Users\chaha\.zengin-pon\license-private.pem`（リポジトリ外。**失くすと発行できない**のでパスワードマネージャーにも控える）。
  公開鍵は `src/license.js` の `PUBLIC_KEY`。鍵の再生成は `tools/gen-keypair.js`（既存ファイルは上書きしない）。
- 発行: `node tools/issue-key.js --months 12`（年払い）／`--months 1`（月払い）／`--until 2027-03-31`。台帳 `tools/issued-keys.csv` に追記（gitignore）。
- 更新: 期限が来たら新しいキーを発行して送る。期限切れのキーは画面に「更新するとまた使えます」と出る。
- 台数制限（2台）は技術的に強制しない（規約上の約束）。
- **Free の制限**: 出力対象が20件まで（超過分は表で「Free上限外」）。列の割り当ての記憶（テンプレート）は Pro のみ。Free はページを閉じるまで。
- **Pro の機能**: 件数無制限、テンプレート保存、振込元プロファイル複数、変換履歴（設定で有効化、最新20件、再ダウンロード）、バックアップ／復元（JSON）。
- 「⚙ 設定 → すべて削除」で `zenginpon.*` の localStorage を全消去（共有PC向け）。

### 販売開始の最短手順（Webhook なしで始める）

1. Stripe で Payment Link を2本作る（Pro 月払い ¥480 / 年払い ¥4,800、メール収集ON）。料金ページの「申し込む（準備中）」をそのリンクにする。
2. 決済通知メールを受けたら `node tools/issue-key.js --months 1|12 --memo "<メール>"` でキーを発行し、テンプレ文面で送る（24時間以内）。
3. 月に数十件を超えたら、Misefits の `functions/index.js` を流用して Stripe Webhook → 自動発行・自動送信に切り替える（署名は Cloud Functions の Secret に秘密鍵を置いて同じ `issue` ロジックを呼ぶ）。
4. 月払いの更新は、Stripe のサブスク更新 Webhook で毎月キーを再発行するか、初回に「12か月分のキー」を渡して解約時に失効させない運用（簡単だが解約後も使える）のどちらか。当面は年払いを推し、月払いは Webhook 実装後に本格化。

## 7. 法務・注意点

- ファイル生成だけで送金は行わないので、資金移動業・電子決済等代行業の登録は不要。
- 特定商取引法に基づく表記、利用規約（生成データの誤りによる損害の免責と、ユーザーが銀行画面で内容確認・承認する旨）、プライバシーポリシー（データを送信しない旨）を用意する。
- 弊社はインボイス（適格請求書発行事業者）未登録。領収書は Stripe の自動メールのみで、適格請求書は発行できない旨をサイトに明記済み。
- 振込先口座情報は個人情報。ブラウザ完結でも、localStorage に残す項目は依頼人情報と列割り当てだけにし、振込先データは保存しない（現状そうなっている）。
